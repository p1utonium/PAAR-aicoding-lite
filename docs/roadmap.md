# 优化开发地图

方向：用户负责业务，AI 负责工程。是否优化成功，以真实任务中的用户干预和记录维护负担为准，不以新增多少规则、工具或页面为准。

## 阶段 1：精简执行路径与地图接入

核心目标：在第一轮就直接消除重复规则、重复登记和看板快照维护。

主要工作：一个 AGENTS.md 入口；一份 work/current.json；同一份记录生成检查结果、接续说明与地图；保留证据、必要确认和失败停止；覆盖文件损坏、无效完成、依赖错误和重新读取。

风险：负担转移到 JSON 却没有减少；必要证据被删；显示上次数据却误报实时成功。

通过依据：这些结构和异常行为有验证证据；用户完成一次地图及接续体验。真实开发效率还不能在此阶段宣称成立。

为什么先做：这是直接处理“重”的最短路径。地图从一开始进入新路径，可以及时发现新方法是否让进度不可见。

## 阶段 2：真实任务减负对比

核心目标：检验结构精简是否转化为实际省事。

主要工作：选一个现有真实需求，记录启动准备步骤、用户确认次数、重复维护动作、用时、失败返工、验收是否通过；与难度接近的旧记录或受控任务对照。旧记录缺少耗时就标未知，不倒推出节约比例。

风险：任务难度、作者熟悉程度、模型差异影响对比；单个成功样本不能证明普遍可靠。

通过依据：维护负担有实际下降，业务验收标准没有放宽；如未下降，先删减或修正当前方案。

为什么第二步做：继续建设 R5 或入口产品之前，先确定轻量方向有效，避免以新工具替代旧工具却没有解决负担。

## 阶段 3：多闭环 R5 与需求变更

核心目标：用少量约定支持真实复杂业务，并证明整体结果。

主要工作：多任务依赖、共享接口、变更影响、失败与恢复、接续，以及整体正常和异常流程验收。只在前一阶段揭示的缺口上增加最少机制。

风险：重新膨胀为流程引擎；把“所有任务完成”当作“整体可用”；为了复用提前建设并行。

通过依据：整体验收与局部验收都有可复核证据；每个新增机制可以对应到实际失败样例。

为什么此时做：复杂性应由真实业务触发。先验证单闭环减负，再承担多闭环组织成本。

## 阶段 4：新手独立试用与定版

核心目标：不熟悉开发的人能在明确范围内完成任务。

主要工作：邀请未参与设计的人使用；记录他们何时停住、误解状态、要求作者代操作；验证业务说明、必要确认、查看结果、失败求助和明确验收；再决定是否需要更友好的启动、表单或安装包装。

风险：作者全程指导导致假成功；包装掩盖模型错误；“只懂业务”被夸大为任意复杂开发都无需专业判断。

通过依据：预先约定试用任务与通过标准，新手完成且作者介入有记录；说清适用范围后发布试用版。

为什么最后定版：入口设计来自真实卡点。提前造桌面应用、插件平台或调度系统，会增加尚未证明必要的工作。

## 阶段之间的决策

工具验证通过与用户体验验收分开记录。每阶段可以缩小、停止或返修，不自动创建更多任务。费用、公开发布、重要数据变更和验收标准改变仍需要相应授权。
