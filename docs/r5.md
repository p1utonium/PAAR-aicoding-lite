# R5 使用方法

R5（Requirement Five-Stage Process）负责复杂需求的整体闭环。PAAR 负责其中一个有边界的实施任务。两者不是竞品，也不应该各自维护相同进度。

## 什么时候使用

由 AI 判断：一个任务的 Review 是否足以证明整个业务结果可用？如果可以，保持 PAAR。如果必须组合多个交付物、共享接口或数据约定，或者必须验证跨步骤失败与恢复，则按需采用 R5。文件多、术语多本身不构成升级理由。

以“客户跟进后自动生成提醒”为例，客户数据录入和提醒显示各自可用，仍不能证明记录变更后提醒会同步取消；需要一个整体场景来验证。

## 五阶段和轻量落点

| 阶段 | 工作内容 | 当前如何记录 | 什么时候返回此阶段 |
|---|---|---|---|
| 1 需求分析 | 明确用户场景、正常和异常行为、范围、未知事项、整体验收条件 | goal、scope、decisions；复杂业务说明按需独立成文并引用 | 根本需求歧义或业务目标变化 |
| 2 任务拆分 | 找出最少可验证交付、依赖、共享约束及集成点 | tasks、depends_on；最后设整体集成验证节点 | 发现拆分遗漏或依赖不成立 |
| 3 方案与验收约定 | 定义职责、输入输出、失败与恢复、验收触发和证据 | 各节点 acceptance 与已确认 decisions；必要的接口约定独立引用 | 实施约定不可执行或发生重大变更 |
| 4 开发组织 | 按依赖串行执行，每个任务运行 PAAR，检查真实改动 | 同一 tasks 列表中的状态、阻塞和下一步 | 约定冲突返回阶段 3；需求错误返回阶段 1 |
| 5 整体集成验收 | 验证完整正常路径、异常路径、恢复、回归及业务结果 | 集成节点验收项与真实证据；用户确认后才 done | 缺少拆分返回阶段 2；缺陷按影响范围返修 |

方案文件用于表达无法在短记录中讲清的共享约定，不默认新增表格和台账。用户确认业务影响与重大取舍，AI 负责低风险技术细节。

## 局部通过与整体通过

“保存成功”和“提醒列表展示成功”只能证明两处局部行为。整体场景应说明：

1. 前提：已有一条客户跟进记录。
2. 操作：设置提醒后修改或取消跟进。
3. 预期：提醒随业务规则正确改变，不重复、不遗漏。
4. 证据：实际测试或可复核操作记录。
5. 未证明事项：例如多人同时编辑尚未覆盖。

当前记录没有“有条件通过”状态。若只完成部分范围，要明确写出限制和未完成条件，保留未通过状态；不能自动把缺证据项目当成已验收。

## 当前实现边界

v0.1 支持节点依赖、串行执行约束和验收记录；它没有自动 R5 路由器、五阶段引擎、合同解析器、派发系统或并行调度。phase 仍只表达当前 PAAR 阶段。上述五阶段是指导方法，复杂业务的实际适用性将在开发地图阶段 3 验证。不能把这份说明当作 R5 已经端到端验证通过。
