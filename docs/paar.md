# PAAR 使用方法

本仓库的默认执行入口是根目录 AGENTS.md。本说明是按需参考，不要求每次任务全文阅读。

## 一次任务的实际操作

**Plan**：AI 先阅读当前记录和相关文件，判断用户说法是否与事实冲突。把结果缩小到一个可以展示的行为，例如“保存跟进记录，关闭后重新打开仍能读取”。在 scope 中限定写入范围和排除项，在 acceptance 中列出可观察的条件。看起来合理的技术推断仍标明待验证。

**Ask**：检查是否还有会改变业务结果、数据权限、费用、公开发布或验收标准的问题。有就用业务语言问；没有就继续。已授权的实现不重复请求继续。不要要求用户选择模块、模型、技能或路由。

**Act**：AI 在范围内完成修改。只有决定、进度、阻塞或证据改变时才更新当前记录，不逐条复制操作日志。新增发现若不影响当前交付就暂缓，不自动增加任务。相同失败连续两次且没有新证据时，停止类似修改，保留错误并调整诊断。

**Review**：核对实际文件变化和验证输出。记录每项验收条件的 pending / passed / failed；passed 必须引用证据文件。验证通过先记 awaiting_acceptance。用户明确确认业务验收之后才记 done，并如实填写 accepted_by。工具并不替用户判断业务是否满意。

## 一份记录如何承担协作

- goal / scope：目标和边界。
- phase：当前思考阶段，取 Plan、Ask、Act、Review；不是一套自动驱动开发的状态机。
- decisions：已确认且仍相关的业务决定，不重复问用户。
- tasks：少量业务闭环节点，id 只是本记录内的关联短名，不需要全局编号。
- acceptance：观察条件、当前结果、项目相对证据文件路径。
- blocker / next_action：失败原因及下一步；阻塞不能只写“继续处理中”。
- updated_at：最后一次实质更新的时间。

一次只执行一个任务；需要依赖的任务只有在前置节点 done 后才能进入 in_progress 或 verifying。未来若实际场景需要并行，再另行设计，当前不维护锁和派发队列。

运行 brief 可以把上述事实转成接续说明。接续后仍需对照真实代码、Git 改动和证据，不能只相信摘要。记录文件的修改应完整写入；写入一半造成短暂无效时，地图提示更新失败并等待下次有效版本。

## 保留什么，删除什么

保留最小业务目标、关键确认、真实验证、失败止损和下一步。小任务不再强制任务卡、路由表、候选转正式、派发回执、状态投影同步。证据文件用于支持具体结论，不充当第二份当前任务记录。

用户的典型参与是：描述业务 → 回答必要问题 → 看结果并验收。当前尚需验证这一操作方式在陌生新手中的可用性。
