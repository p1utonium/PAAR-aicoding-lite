# 旧机制的通用结构与减负取舍

本文整理可复用的方法，不复制业务工程、历史任务、机器配置或运行数据。

## 原执行方式

一个任务通常从读取规则和能力路由开始，形成任务计划，必要澄清后实施，再检查验收、任务卡和状态。复杂需求先经历 R5 分析、拆分、方案与验收约定；候选任务转成正式任务后登记到执行系统，按依赖和所有权派发；每个任务完成 PAAR 后，再做需求级集成验收。

配套记录包括任务卡、候选或正式属性、当前任务、队列、看板、所有权、锁、派发、事件和验证日志。任务完成可能需要同步多个记录和派生视图。其好处是可以追溯复杂组织过程，代价是更多固定读取、维护和检查动作。

## “重”的原因

1. **治理范围超过当前工作规模**：为多人、并行和复杂集成准备的成本进入了普通小任务。
2. **同一事实有多个表示**：任务状态、执行状态和看板状态需要协调；自动生成也仍需要维护生成链和排查失败。
3. **方法与运行系统耦合**：想用 PAAR 就要先理解配套文档及路由、登记、派发规则。
4. **用户被拉进内部决策**：原原则本来允许 Ask 按需跳过，实际执行仍可能过度确认；这既涉及规则表达，也涉及模型遵循，不能仅删文件就保证解决。
5. **记录齐全容易被误读为交付成立**：流程一致性检查不能替代代码、异常场景和用户体验证据。

## 本版取舍

默认单写入者，省去小任务的并发锁与派发管理；统一一份当前记录，地图和接续说明即时从它生成。保留验收条件、关键决定、失败信息和必要的证据报告。历史审计能力、并行协作和自动执行能力因此不属于当前版本承诺。

没有将旧体系的所有字段搬到一个巨大文件中。当前短记录只支撑本轮和少量后续闭环，最多 100 个节点；复杂接口说明按需引用。这个容量上限只是实现边界，不是性能承诺。

结构精简已经体现在代码中；耗时、模型上下文消耗、用户提问次数是否下降，仍需真实任务测量。
