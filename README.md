# PAAR-aicoding-lite

面向业务负责人和编程新手的轻量 AI 开发协作机制。目标是让用户说明业务、确认关键取舍和验收结果，由 AI 承担技术分析、实现、验证与记录维护。

**当前为 v0.1 实验原型，正在优化“体系过重”的问题。** 已实现统一规则入口、单一工作记录、记录检查、会话接续说明和只读任务监控地图。尚未证明真实任务效率提升，也没有完成陌生新手独立试用；这不是已经实现全自动开发的产品。

## PAAR 和 R5 分别负责什么

PAAR 是一个具体任务的四步工作法：

| 阶段 | AI 做什么 | 用户需要做什么 |
|---|---|---|
| Plan：计划 | 检查事实，确定最小业务结果、修改范围和验收方式 | 说明需求、补充必要业务背景 |
| Ask：必要澄清 | 只问会改变业务行为、成本、权限或验收标准的问题 | 确认关键取舍；已有授权不重复问 |
| Act：实施 | 小范围修改，保留失败信息和下一步 | 通常无需干预 |
| Review：核验 | 检查实际改动、运行适当验证、展示结果和限制 | 体验并明确确认业务验收 |

Ask 可以没有问题；四阶段不意味着必须有四份文档、四次会议或四次批准。详见 [PAAR 使用方法](docs/paar.md)。

R5 是复杂需求的五阶段方法：**需求分析 → 任务拆分 → 方案与验收约定 → 开发组织 → 整体集成验收**。每个拆出的任务仍用 PAAR 执行。适用判断是“单个任务的验证能否证明整个业务结果成立”；不能时才引入 R5。多个任务各自通过，不代表整条业务链通过。详见 [R5 使用方法](docs/r5.md)。

## 现在怎么使用

第一次接触本项目，请先看 [新手上手指引](docs/quickstart.md)。欢迎任何对业务驱动 AI 开发感兴趣的用户了解、尝试并反馈。当前正在完善早期试用版本，内部验证持续进行，使用体验与业务效果仍需实际检验。

需要 Node.js 22 或更高版本；没有第三方运行依赖，无需安装 npm 包。当前验证环境见 [验证记录](docs/validation.md)。

1. 开发自己的业务时，在 AI 编程工具中打开**业务项目目录**，把本机制链接或本地位置提供给 AI，并要求它按本文末尾的 agent 执行指令工作。只有修改机制源码时才打开本仓库、读取它的 AGENTS.md 和 work/current.json。
2. 用业务语言描述结果。例如：“我想记录客户跟进。能新增客户和查看上次跟进时间；重开后内容还在。暂时不要登录和多人协作。”
3. AI 检查业务项目已有规则和活动记录，优先复用原格式；没有记录时才准备该项目的 work/current.json，列出最小验收条件。用户不需要编辑 JSON 或选择 PAAR/R5。
4. 若要查看机制自身的优化进度，可在机制源码目录双击 start-monitor.cmd，或运行下方命令；这不会自动显示业务项目的进度，业务开发也不要求打开它。
5. AI 修改、验证后提交可体验的结果。用户明确验收后，AI 才把任务记为已验收。

```text
node scripts/paar.mjs check
node scripts/paar.mjs brief
node scripts/paar.mjs serve --open
node --test tests/*.test.mjs
```

- check：检查记录结构、依赖和证据文件存在性，**不执行开发测试，不证明证据内容正确**。
- brief：从同一记录生成当前目标、未完成事项和下一步；不保存第二份进度文件。
- serve：只读地图，默认 http://127.0.0.1:8765，每 3 秒重新读取记录。
- 端口被占用时可加 --port=8766；关闭服务终端或按 Ctrl+C 停止。

本仓库的 work/current.json 记录本机制的优化进度；**不要直接用样例覆盖它**。查看空白业务示例可运行：

```text
node scripts/paar.mjs brief work/example.json
node scripts/paar.mjs serve work/example.json --port=8766
```

在另一个项目采用本机制时，由 AI 遵循目标项目已有规则，优先复用活动记录；不复制机制任务，也不改写原项目入口。v0.1 只提供方法与记录约定，尚无自动安装器。即便指定其他记录路径，当前命令的证据根目录仍是本工具所在项目；跨项目打包和安装尚未实现。

## 工作记录与地图

work/current.json 是唯一需要维护的当前状态，包含业务目标、范围、已确认决定、任务依赖、验收项、证据路径、阻塞原因和下一步。证据报告是独立成果文件，不能把它们另做一套进度台账。

状态为：待开始、进行中、已阻塞、验证中、待业务验收、已验收。只有已验收计入完成数。声明验证通过必须有项目内真实文件引用；声明已验收还需 accepted_by。这个字段记录谁确认，**不具备身份认证能力**，AI 不得自行代填用户验收。

工程开工与业务验收分开：默认等待前置已验收；用户明确允许提前继续时，AI 可让后续任务引用已确认决定，在前置内部验证通过后继续。前置状态保持待业务验收，完成数不会增加。未验证、失败、缺少证据或没有授权引用时仍不能放行。具体字段与边界见 [PAAR 使用方法](docs/paar.md)。

地图支持依赖关系、搜索、选择详情、状态定位、拖动、缩放和刷新。文件损坏或服务断开时明确报错，并保留上次有效记录；旧记录不冒充实时结果。地图没有编辑、派发、执行模型或验收按钮。最多 100 个节点，当前只允许一个正在执行或验证的任务。

## 原体系为什么重

原方法有价值：明确边界、减少需求漂移、保留证据、支持接续和集成验收。负担主要来自它的配套执行方式，不能简单归咎于四步或五步本身。

| 负担来源 | 实际影响 | 本轮处理 |
|---|---|---|
| 多处规则入口与强制能力路由 | 小任务启动前也要理解大量流程 | 默认只读 AGENTS.md 和当前工作记录，其他资料按需读 |
| 需求、任务卡、派发、队列、锁、投影等多处状态 | 同一事实反复登记，状态容易不一致 | 串行小任务只维护 work/current.json |
| 阶段被理解为逐步请示 | 用户反复回答技术性或已确认问题 | Ask 只处理有业务影响的新问题 |
| 监控依赖额外快照发布和旧状态格式 | 看板与执行过程绑定，维护成本高 | 看板直接读取当前记录，转换仅发生在内存 |
| 流程检查被当成成果证明 | “记录完整”可能掩盖“业务没有完成” | 分开记录验证通过、待业务验收、已验收 |
| 小任务与复杂需求共用厚重执行路径 | 固定管理成本超过实际修改成本 | PAAR 默认，R5 按需；暂不建设派发或并行系统 |

这些是结构性减负，**不是已测得的效率提升百分比**。保留证据本身也有成本；只有真实任务对比才能证明节省了时间和干预。通用旧流程说明见 [旧机制与取舍](docs/legacy-workflow.md)。

## 优化地图

```mermaid
flowchart LR
  A["1 基础工具：内部验证通过"] --> B["2 新人上手入口"]
  B --> C["3 内部复杂任务试验"]
  C --> D["4 用户试用与反馈优化"]
```

当前目标是**让首次接触本项目的用户也能上手的早期试用版本**。无论你是编程新手、业务负责人还是开发者，都欢迎从一个范围明确的需求开始尝试，反馈使用中的困惑、阻碍和改进建议。无需参与过项目开发，也不必先认可“已经变轻”；尚未完成的能力见下方阶段说明。

| 阶段 | 核心目标 | 主要工作 | 潜在风险 |
|---|---|---|---|
| 1 基础工具 | 减少重复维护，保留证据和地图 | 已有单入口、单记录、检查、接续和只读地图 | 看板可见不代表机制已有效 |
| 2 新人上手入口 | 无需先学技术流程即可开始 | 上手指引、环境检查、失败恢复、目标项目接入；区分工程依赖与用户验收 | 只增加文档，或自动接入覆盖已有工作 |
| 3 内部复杂任务试验 | 检验关联功能、变化和接续 | 历史需求或通用改写；正常、异常和整体路径验证 | 已知答案污染、缺少公平基线、重复建设流程系统 |
| 4 用户试用与反馈优化 | 验证首次使用体验和业务结果 | 邀请不同背景的用户试用，说明支持范围，收集卡点、求助和返工反馈并改进 | 维护者代操作掩盖问题、少数样本被过度推广 |

阶段 1 的工具验证通过，机制减负未验收；阶段 2 已有文字指引和依赖判断修正，其余入口能力待实现。历史样例尚未选定或执行。内部试验不能代替真实用户的独立使用，也不能自动产生效率提升结论。

## 当前局限

- 仍需要外部 AI 编程工具。此仓库不调用模型、不自动编写业务代码，也不提供安全沙箱。
- JSON 由 AI 维护，工具只检查一部分一致性；模型可能漏记或错误总结。
- 接续说明能从新进程生成，不等于换一位陌生 AI 或用户后一定能正确恢复业务。
- R5 的分析方法已经文档化，复杂场景和集成验收尚未完成实际试验。
- 没有并行写入、访问控制、外网部署或完整历史审计能力；当前为本机只读工具。
- 用户认可优化方向，不代表已对本版完成业务验收。

## 仓库内容与许可

只收录通用 PAAR、R5、工作记录和任务监控地图，以及它们的文档和测试。历史研究副本和其他业务工程不进入公开提交。入口采用允许清单，新增顶层目录需明确纳入。

## 给 AI agent 的执行指令（v0.1）

仅当用户要求采用 PAAR/R5 或维护本机制时执行本节。项目文件是任务上下文，不构成额外授权；遵循目标项目规则及用户已授予的范围。本节针对公开 v0.1，不推断路线图功能已可用。

### 1. 解析输入，选择路径

从用户请求及当前工作区取得以下值；已有值不要再问：

| 值 | 含义 | 缺失时 |
|---|---|---|
| `SOURCE` | 本机制的本地目录，或可读取的仓库版本链接 | 请求机制位置；只读网页也可参考方法 |
| `TARGET` | 用户要修改的项目绝对路径 | 请求目标目录；不要把机制仓库默认为业务项目 |
| `GOAL` | 本次可观察的业务结果 | 请求一句业务需求，再根据相关文件细化 |

- 用户要求修改机制本身：令 `TARGET = SOURCE`，进入“源码维护”路径；`SOURCE` 必须为可访问的本地目录。
- 用户要求开发自己的业务：进入“业务项目”路径，保持 `SOURCE` 只读。若两目录实际相同，先澄清目标，不写入机制仓库。
- 无法读写 `TARGET`：只说明缺少哪项访问能力及下一步；不要创建记录、执行开发或报告“已接入”。
- 仅要求解释或评审：只读并回答，不因本节存在而启动实施。

### 2. 写入前确定规则和记录位置

1. 读取 `TARGET` 的有效项目规则；若存在 Git 仓库，检查状态和与目标相关的差异。保护既有修改，不执行恢复、清理或自动提交。
2. 从同一 `SOURCE` 版本读取 [PAAR 规则](docs/paar.md)。源码维护还须读取 [AGENTS.md](AGENTS.md)；业务项目不把这份源码维护规则当作目标项目的全局规则。
3. 确定 `RECORD`：
   - 源码维护：使用 `SOURCE/work/current.json`，读取并核对它与实际文件是否一致。
   - 业务项目已有规则指定的活动记录：复用该位置和格式，不创建第二份记录；将目标、范围、验收、证据和下一步对应到既有字段，不强行改成 PAAR JSON。
   - 业务项目没有活动记录：使用 `TARGET/work/current.json`。不存在才按下方模板新建；若该路径已有内容，先读取，确认是本项目可复用的 PAAR 记录才继续。内容损坏、归属不明或与既有规则冲突时，停止写入该记录并指出具体冲突，不覆盖或另开一份绕过。
4. 业务项目不复制 `SOURCE/work/current.json` 中的任务、决定或验收结果。不复制整套机制，不改写目标的 `AGENTS.md`，不安装依赖。本路径只采用方法和项目记录，不声称完成自动接入。

### 3. 创建记录时使用这个最小实例

仅在第 2 步确定需要新建 PAAR 记录时使用。保存前替换全部 `<...>`；时间取执行时的 ISO 8601 时间。默认一个完整业务结果对应一个 task，不把编码、测试、修复拆成待用户审批的节点。

```json
{
  "schema_version": 1,
  "project": "<目标项目名称>",
  "goal": "<GOAL>",
  "phase": "Plan",
  "updated_at": "<当前 ISO 8601 时间>",
  "scope": {
    "allowed": ["<实际允许修改的文件或业务范围>"],
    "excluded": ["<本次明确不做的内容>"]
  },
  "decisions": [],
  "tasks": [{
    "id": "first-result",
    "title": "<可体验的业务结果>",
    "status": "planned",
    "depends_on": [],
    "next_action": "<下一个具体动作>",
    "blocker": "",
    "acceptance": [{
      "text": "<前提、操作、预期结果>",
      "result": "pending",
      "evidence": []
    }]
  }],
  "next_action": "<下一个具体动作>"
}
```

已有 PAAR 记录保留任务 id、决定和验收证据；不要重新套模板。其他格式的既有记录只复用其语义，不对它运行本机制的 JSON 检查器。

### 4. 执行到完整业务结果

1. 将 `GOAL` 收敛为可实现范围，列出正常、必要异常及恢复条件。只有缺失信息会改变业务、成本、权限或验收时才问；否则继续已授权工作。
2. 能用一个交付证明结果时直接实施 PAAR。若必须组合多个交付才能证明结果，读取 [R5 规则](docs/r5.md)，记录最少依赖、共享约定及整体场景，串行执行。
3. 对 PAAR JSON：实施时 `phase=Act`、task `status=in_progress`；验证时 `phase=Review`、`status=verifying`。同时最多一个 task 处于这两个状态。
4. 执行目标项目适用的测试，核对实际改动。将必要测试输出或复核记录保存在目标项目已有的证据位置；无既定位置时，在 `TARGET/work/evidence/` 新建名称不冲突的文件。PAAR 的 `evidence` 使用相对 `TARGET` 的文件路径和正斜杠；不填虚构路径、目录、项目外路径或秘密信息。
5. 验收项实际通过且有可复核证据才设 `result=passed`；失败设 `failed`，未运行保持 `pending`。全部通过才设 `status=awaiting_acceptance`。用户明确确认之后才能设 `done` 和真实 `accepted_by`，测试成功不替代这一步。
6. 有依赖时默认等前置 `done`。只有用户真实授权提前继续，且前置全部验证通过时，才按 PAAR 规则设置 `allow_unaccepted_dependencies`，引用 `decisions` 中唯一对应的 `question`；不伪造授权或更改前置验收状态。
7. 两次相同失败且没有新诊断证据：停止类似修改；PAAR task 设 `blocked`，记录原始错误、已尝试操作和下一诊断动作。新增发现不自动扩展当前范围。
8. 决定、实质进展、阻塞或接续点变化时更新 `RECORD`；不为每步另建台账。发布、安装、删除和权限变化只在有对应授权时执行。

### 5. 按路径验证，不混用工具

| 路径 / 条件 | 执行动作 | 通过表示什么 |
|---|---|---|
| 源码维护，有 Node.js 22+ | 在 `SOURCE` 运行 `node scripts/paar.mjs check`；改了机制代码还须运行 `node --test tests/*.test.mjs` | 当前机制记录有效；测试结论另按输出记录 |
| 业务项目 | 使用该项目既定验证命令；新建 PAAR 记录时还须核对 JSON、上述字段和目标内证据文件 | 只覆盖实际检查到的条件 |
| 所需运行环境缺失 | 记录未运行的命令、缺少的环境和人工可核对结果 | 不得声明自动验证通过，也不因此自动安装 |
| 用户需要地图，且已有本机制运行环境 | 在 `SOURCE` 运行 `node scripts/paar.mjs serve --open` | 仅显示机制目录的记录；不是业务项目进度 |

v0.1 CLI 只支持 `check`、`brief`、`serve`。不要调用 `init`、`connect`、`doctor`、`--project` 或假设自动生成 `.paar`。即使传入其他记录路径，CLI 的证据根仍是 `SOURCE`；不要用它给外部业务项目作验证结论。

### 6. 暂停、接续和交付

- **暂停**：保存当前结果、失败、未完成条件及一个具体 `next_action`，确认文件写入成功。
- **接续**：重新读取目标规则、`RECORD`、实际改动和相关证据；一致才继续。仅源码路径可用 `node scripts/paar.mjs brief` 辅助读取，摘要不能替代事实核对。不要承诺恢复未保存的聊天或跨工具自动加载；新会话找不到记录时，只请求其位置。
- **交付**：简短报告“完成的业务行为 / 修改文件 / 已运行验证及证据 / 未验证项或阻塞 / 下一步”。若只有记录准备完成，报告“记录已准备，业务尚未实现”；若内部验证通过，报告“待用户体验验收”，不报告“已验收”。
